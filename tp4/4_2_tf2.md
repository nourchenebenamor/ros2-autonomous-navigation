## Quick introduction

In our robot we have several frames attached the different parts (wheels, body, sensor...). Those frames can be displayed on rviz by adding a `TF` visualization:

![Robot tf](images/tp4_robot_tf.png)

Here we have 5 different frames:
- base_link
- back_castor_wheel_link
- front_castor_wheel_link
- left_wheel_link
- right_wheel_link

All those frames are connected together via the `base_link` frame (as defined in the urdf file).

In ros2, the tf2 library handles all the frame stuff.

> tf2 is the transform library, which lets the user keep track of multiple coordinate frames over time. tf2 maintains the relationship between coordinate frames in a tree structure buffered in time and lets the user transform points, vectors, etc. between any two coordinate frames at any desired point in time.
> https://docs.ros.org/en/jazzy/Concepts/Intermediate/About-Tf2.html

The frames can also be checked with the `tf2_tools` package:

```bash
ros2 run tf2_tools view_frames
```
This command will listen for the tf during 5s and then will create a pdf with the connection between the different frames. **Warning: the pdf file will be created in the current directory!**

![Robot tf](images/tp4_frames.png)

In the `fixed Frame` menu of `rviz` you can change the reference frame. As all the frames are connected to each other, everything will be displayed but the position/orientation may vary according to the origin of each frame.

## The world frame

When moving the robot you can notice that in `rviz` it is the LiDAR data that moves, but the robot stay at the origin of the display. It is because the display in `rviz` is done according to the `Fixed Frame` (`base_link` in our case).

What we would like now is to have the position of the robot in the simulated world. To do that, classically, we use a localization algorithm to be able to compute the position of the robot according to the measurement data (the LiDAR here). But to ease this part, we will consider that we already have the robot pose (position and orientation) and use the one provided by gazebo.

### Create a tf broadcaster

Gazebo provides the pose of the robot in the environment (world). This pose (on the `/model/tp4_robot/pose` topic in gazebo) is redirected into the ros2 environment in the `/pose` topic (you can check the bridge configuration to get those infos).

From what you have done so far, and according to https://docs.ros.org/en/jazzy/Tutorials/Intermediate/Tf2/Writing-A-Tf2-Broadcaster-Py.html 
create a node named `world_tf_broadcaster.py` that will broadcast a transform between the `dummy_root_link` (that is the root of the urdf link and has a fixed joint to the `base_link`) frame and the `world` frame according to the robot's pose.

Create a new launch file named `world_tf_launch.py` that starts:
- gazebo (you can call the `gazebo_launch.py` file of the `tp4_description` package)
- rviz with a custom configuration (the main frame should be the `world` frame)
- the world tf broadcaster 
- the teleop node

(do not forget the `use_sim_time` parameter).

When running your launch file, you should be able to display your simulation in the `world` frame:

![Robot tf](images/tp4_tf.gif)

### Advices

The `/pose` is of type/interface `geometry_msgs/msg/PoseStamped`. In the `/pose` topic you have the poses of all the elements of the robot (wheels, body...). The pose that you are interested in is the pose with the `header.frame_id == 'my_world'`.

If you have strange behavior while displaying rviz with the world frame, first check that you set `use_sim_clock` properly, then you should check the pose sent by gazebo
```
gz topic --echo --topic /model/tp4_robot/pose
```
and the ones available on ros2
```
ros2 topic echo /pose 
```

You can also check if several instances of gazebo are running:
```
ps -aux | grep gz
```
and if there are, you must kill them
```
kill -9 <ID>
```
the `-9` is to force the program to shut down
